## 1. 背景与目标

### 1.1 背景

- 企业内部文档类型多样（**纯文本 TXT、Word、PDF、PPT/PPTX、Markdown、Excel** 等），总量可达**数十 GB**。
- 需将文档内容**向量化**后写入 **Qdrant**，支撑语义检索与问答；在**已通过部门权限过滤**的检索结果之上，可调用**自建 vLLM 服务**上的 **通义千问 Qwen3-30B-Thinking** 对内容进行**润色与综合表述**（见 **§5.2.1**、**§12.4**）。
- **Qdrant 以 Docker 容器部署**，并自带基于浏览器的 **Dashboard / Web UI**（一般与 HTTP API **同端口**，路径多为 **`/dashboard`**，随镜像版本以官方为准），用于集合浏览、数据巡检与调试。业务检索仍以**自研 Web + API**为主；Dashboard 作为**运维/管理员**辅助工具，经 **§5.2.2** 在管理端提供**按钮跳转**即可，**不必**把 Dashboard 内嵌进业务页为默认方案。  
- **向量化（Embedding）**在 PRD 中**不锁定**某个具体公开模型；实现期采用 **本地推理** 或 **企业内网 Embedding HTTP API**（见 **§12.5**）均可。**索引写入与检索查询必须使用同一模型与同一向量维度**；模型标识写入 `embedding_model_version`（任务 payload / 元数据），便于升级与全量重嵌入。

### 1.2 目标

| 编号 | 目标 |
|------|------|
| G1 | 提供统一 **Web 界面**：浏览索引状态、上传/删除/更新文档、按权限管理，全员可使用检索入口。 |
| G2 | **检索**：支持多用户并发提问；**入库**：支持并发上传，上传后**排队并优先即时向量化**，可做一次**可观测的自检/试搜**。 |
| G3 | **定时任务**：每日**凌晨 1:00**（可配置）对**新增/变更/待补偿**文档做批量向量分析与索引更新；并执行 **向量对账删除**：确保**已在 Web 端删除**（或元数据已移除）的文档在 **Qdrant 中不再残留**（见 **§5.5**、**§8**）。 |
| G4 | **权限与部门范围**：对接公司 **EHR 组织（最多 5 级部门）**；**上传时**由上传人指定**哪些部门及其范围**可检索该文档；**用户仅能在本人所属部门范围内**检索到被授权的知识（见 **§5.3**）。文档**增删改**仍按角色与所有权控制。 |
| G5 | 流水线**可恢复、可观测**：任务状态、失败原因、重试与幂等。 |
| G6 | **检索可溯源**：向量命中结果须展示**可读的物理/逻辑文件路径**，并尽量给出 **PDF/Word 等页码**、**PPT 幻灯片序号**、**Excel 工作表名（Sheet）与行区段** 等，支持用户打开源文件并定位到具体位置（见 §5.1.1）；**Excel 须对文件内全部工作表分别解析与建索引**（见 §5.1）。 |
| G7 | **运营可视与审计**：Web 提供**管理看板**，汇总**文档数量**、**向量点数量**、**按日统计的用户操作次数**（及可选维度拆分）；提供**操作日志**页面，支持按用户、操作类型、时间范围等**查询每一条**已记录行为（见 **§7.4**、**§11.1～§11.2**）。 |
| G8 | **检索后大模型润色**：在 **Qdrant 向量检索**（已按 §5.3.3 部门过滤）返回的 Top-K 片段基础上，由服务端调用 **vLLM** 提供的 **OpenAI 兼容接口**，使用 **Qwen3-30B-Thinking** 生成**结构化、可读的综合回答**，并**绑定可追溯引用**（路径、页码/Sheet/行等，与 **G6** 一致）；**不得**基于未检索到的内容臆测；LLM 不可用时**降级为仅展示向量命中列表**（见 **§5.2.1**、**§12.4**、**§13.2**）。 |
| G9 | **对外 HTTP API**：在 **Web 之外**提供 **RESTful JSON API**（与 `cursor-rules` 统一响应结构），供 **OpenClaw**、脚本、其它业务系统**直接调用**完成**知识库检索**（及 TDD 中扩展的上传/任务查询等）；发布 **OpenAPI 3** 描述文件；支持 **用户 JWT** 与 **API Key** 两类鉴权，**强制**与 Web **共用** §5.3.3 **部门范围过滤**与 **G6** 溯源字段（见 **§5.9**）。 |

## 2. 范围与非目标

### 2.1 范围内

- 文档解析 → 分块 → 向量化 → 写入 Qdrant。
- 元数据与任务状态持久化（关系库或等价存储）。
- **对外 HTTP API**（**G9**）+ Web 前端（管理 + 检索）+ **部门维度可见性**（EHR 同步与上传勾选）+ **管理看板**与**操作日志查询**（管理员，见 **G7**）+ **vLLM 检索后润色**（见 **G8**）。
- Docker Compose（或后续 K8s）下的服务编排骨架。
- 即时队列与定时批处理**双轨**索引策略。

### 2.2 范围外（可列为后续迭代）

- 多租户 SaaS 级隔离（若仅单企业可简化为单租户 + 组权限）。
- 换用非 Qdrant 的向量库。
- 复杂工作流审批（如公文多级审批）；PRD 仅预留扩展点。

## 3. 用户与场景

### 3.1 角色（示例）

| 角色 | 说明 |
|------|------|
| 访客/全员用户 | 可使用**检索/问答**入口（具体数据范围见权限）。 |
| 文档贡献者 | 对其有权限的库/目录**上传、更新、删除**文档，触发索引。 |
| 知识库管理员 | 全库或所辖范围的管理、失败任务处理、配置批处理窗口；使用 **管理看板**与**操作日志**做汇总与审计追溯（**G7**）。 |
| 系统 | 定时批处理、Worker 消费队列。 |

### 3.2 核心场景

1. **上传文档**：用户在 **Web 文档库**录入/上传 → 鉴权通过 → 文件落存储 → 创建**向量化/索引任务**（高优先级）→ 返回 `job_id`，前端轮询/WebSocket 直至 `indexed` 或 `failed`。  
2. **即时“可测试”**：任务完成后，系统可对**该文档**执行一次探针检索或状态翻转，前端引导用户试搜。  
3. **更新/删除文档**：有写权限用户在 **Web 端**对**文件/文档**执行更新或删除 → **删除**时须触发 **按 `doc_id` 清理 Qdrant**（见 §8「即时删除」）；若即时清理失败或采用软删策略，**凌晨 1:00 批处理**再次 **对账删除**向量，保证**已删文件**不在检索中出现。更新时：元数据与内容变更 → 删旧向量后重索引或等价策略。  
4. **全员提问**：多路并发检索 → embedding → Qdrant 查询 → **部门权限过滤**（§5.3.3）→ 返回片段与 **文件路径 + 页码/幻灯片/表格区域（含 Excel 具体 Sheet）** 等定位信息（§5.1.1）；可选（**已定**，G8）→ 将 Top-K 片段送入 **vLLM + Qwen3-30B-Thinking** 生成**润色/综合回答**并带回引用。**OpenClaw 等经 HTTP API（G9）检索与上述数据面一致**。**同一 `.xlsx` / `.xls` 内任意工作表中的文本均应可被检索命中**，不得出现「只有第一个表能搜到」的情况。  
5. **凌晨批处理**：扫描“待批处理”标记或 **hash/mtime 不一致** 的文档 → 低优先级队列消费 → 更新向量索引；**并**执行 **§5.5** 所述 **已删除文档的向量对账清理**。

## 5. 功能需求

### 5.1 文档与索引

- **支持格式（解析入库）**（可在实现期按优先级分阶段，MVP 可先 TXT/MD/DOCX）：  

| 类别 | 扩展名（示例） | 说明 |
|------|----------------|------|
| 纯文本 | `.txt`、`.log`、`.csv`（按文本读时） | 需处理 **编码探测**（UTF-8 / GBK 等），异常字符过滤或替换；大文件流式读取。 |
| Word | `.docx`（优先） | 现行标准：段落、页眉页脚、表格内文字；可选跳过修订痕迹策略。 |
| Word 旧版 | `.doc` | **二进制 OLE**，建议依赖 **LibreOffice/antiword** 等外部转换或统一在上传时转为 DOCX（产品策略二选一）。 |
| 版式/演示 | `.pdf`、`.ppt`、`.pptx` | 同既有规划；扫描件 PDF 可走 OCR 迭代。 |
| 标记与数据表 | `.md`、`.markdown`、`.xlsx`、`.xls` | **Excel（强制）**：须遍历工作簿内 **全部 Sheet（工作表）**，**每个 Sheet 独立分块与向量化**，不得只索引默认第一个表；隐藏表是否入可由配置默认「跳过隐藏表」并在文档中说明。超大表按行窗切片，且 payload 带 `sheet_name`（及可选 `sheet_index`）与行范围。 |
| 其他常见 | `.rtf`、`.html`、`.htm` | **迭代扩展**；RTF 可经转换链或专用库解析。 |

- **上传白名单**：API 与前端需对齐 **MIME + 扩展名** 校验；未支持格式明确提示「暂不入库」或进入「仅存储不索引」。  
- **分块策略**：可配置 chunk 大小、overlap；表格/幻灯片按边界切分，避免单 chunk 溢出上下文；**纯文本**可按段落/固定窗口滑动。解析阶段须**尽量保留与「页/幻灯片/表」对齐的元数据**，以便写入向量点 payload。  
- **Excel 多 Sheet**：入库流水线必须 **for 每个工作表** 执行提取 → 分块 → 写入向量点；检索命中须能通过 **`sheet_name`（及建议的 `sheet_index` 顺序号）** 区分来自不同表的内容；同一文件跨多表时，`file_path` 相同、`sheet_name` 不同。  
- **Qdrant Payload（入库强制）**：每个向量点除向量外必须带可检索的 **溯源与定位** 字段（供筛选与结果展示），**至少**包含下表；缺失字段时用 `null` 并说明原因（如无页概念的纯 TXT 可无 `page_no`）。

| 字段 | 说明 |
|------|------|
| `doc_id` | 文档主键，与关系库一致。 |
| `file_path` **或** `storage_url` | **用户可理解的完整或相对路径**（或内网可解析的存储 URI），用于列表展示与「打开文件」；与 `documents.storage_key` 可映射。 |
| `file_name` | 文件名（含扩展名），便于一眼识别。 |
| `chunk_index` | 文档内分块序号（从 0 或 1 约定统一即可）。 |
| `text_preview` | 该 chunk 正文片段（或摘要），用于结果列表高亮。 |
| `content_hash` / `indexed_at` | 文档级 hash、索引时间（与既有幂等/审计一致）。 |
| `visible_department_ids` | **部门范围检索（强制）**：该 chunk 允许被哪些部门用户检索到的 **部门 ID 扁平列表**（EHR 主键，UUID 或整型依对接约定），在**索引写入时**由上传人勾选的部门范围**展开**后写入（见 §5.3），供 Qdrant **Filter** 与 `must` 匹配当前用户所属部门。 |

| 按格式的定位字段（尽量填写） | 说明 |
|------|------|
| `page_start` / `page_end` | **PDF、Word（DOC/DOCX）**：该 chunk 覆盖的**起止页码**（1-based）；单页则二者相同。 |
| `slide_index` | **PPT/PPTX**：幻灯片序号（1-based）。 |
| `sheet_name` | **Excel**：工作表名称（**必选**，用于区分多 Sheet）；重名表场景须配合 `sheet_index`。 |
| `sheet_index` | **Excel**：工作表**顺序索引**（从 1 或 0 统一约定），与 Excel 内标签顺序一致，避免仅依赖表名导致歧义。 |
| `row_start` / `row_end` | **Excel**：该 chunk 在当前 Sheet 内覆盖的**行号**（含表头策略需在实现文档中固定）。 |
| `section_heading` | **Markdown / 结构化文档**：就近标题路径（如 `一级 > 二级`），辅助人工定位。 |
| `char_start` / `char_end` | **可选**：源文件内字符偏移（纯文本/Markdown 等有稳定全文序列时），用于精细化跳转或二次高亮。 |

- **解析责任**：Loader/分块器在切分时须**透传**解析库返回的页码、幻灯片索引等；跨页 chunk 应 **拆分** 或 **填 `page_start`～`page_end` 区间**，避免「一页都不标」。**Excel** 须枚举全部 Sheet，**禁止**仅处理 `Worksheets(1)` 或活动表；每个 Sheet 产出文本后再走统一分块策略。  
- **幂等**：同一 `doc_id` + 稳定 chunk 规则下，重复任务应先删后写或确定性 point id，避免重复向量堆积；**Excel** 的 point id 或 chunk 键建议纳入 **`sheet_index` + 行/块序号`**，避免跨表覆盖。  
- **索引**：对 `doc_id`、`file_path`（或 `file_name`）、**`sheet_name`（及按需 `sheet_index`）** 等**用于过滤**的 payload 字段在 Qdrant 侧建立 **payload index**（见 §13.1），支持「按文件 + Sheet」筛检与运维对账。  

#### 5.1.1 向量检索结果展示与定位（强制）

- **API / 检索响应**：每条命中除 `score`、向量 id 外，必须返回上述 payload 中与用户相关的字段，**优先醒目标出 `file_path`（或等价）与 `page_start`/`page_end`（或 `slide_index` / `sheet_name` + `sheet_index` + 行号）**。  
- **前端**：结果列表每条展示 **文件路径 + 定位摘要**（例如：`\\share\kb\合同.pdf · 第 3–4 页`；Excel：`报表.xlsx · Sheet「销售明细」· 第 12–40 行`）；提供 **「打开源文件」**（在权限允许下由客户端或内网协议打开）及 **「复制路径」**；若有 **页码**，应传递给查看器或 PDF 阅读器 **直达页**（产品可实现为一键链接带 `page=` 参数，具体依赖内网文档预览组件）。**Excel** 须在摘要中**始终显示工作表名称**（及顺序号若 UI 需要）。  
- **无法用页码的格式**（如无分页的 `.txt`）：须展示 **路径 + chunk 序号/章节标题**；若存在 `char_start`/`char_end`，可在后续迭代支持编辑器跳偏移。  
- **验收**：抽样质检「检索 → 人工能在源文件对应页/幻灯片/**具体 Sheet 与行区域**找到同一表述」；**Excel** 须用**至少含 2 个 Sheet** 的样例文件验证两表均可被搜到。  

### 5.2 Web 功能

- **浏览**：按文档列表/集合维度查看索引状态、chunk 数量、最近错误信息（管理员视图可更细）。  
- **上传**：多文件、进度与任务状态；超过阈值走异步（必做）。**上传表单须包含「可检索部门范围」**：**五级联动/树形多选**（数据来自 **EHR 同步的部门树**，见 §5.3），上传人必选至少一种范围策略（例如：勾选若干部门节点，并可对每节点选择**是否包含下级子部门**）；提交后与文档元数据一并保存，并在向量化时写入每条向量点的 `visible_department_ids`。  
- **删除/更新**：有权限则允许。**删除**须在 **Web 文档库/文件列表**提供明确入口（二次确认）；**正常路径**为：入队 **`delete_vectors`** → Worker **按 `doc_id` 删除 Qdrant 全部相关 points** → 再删存储对象与元数据（顺序见 **§8**）。**凌晨 1:00 批处理（G3）**须包含 **补偿/对账**：对「业务侧已删除但向量仍可能存在」的 `doc_id` 再次执行删除，并可选扫描 **Qdrant 孤儿点**（`doc_id` 在 `documents` 表中已不存在），详见 **§5.5**。  
- **检索**：查询框 + 结果列表（**片段、完整文件路径、页码/幻灯片/Sheet 与行区**、得分）；与 §5.1.1 一致；**Excel** 检索须覆盖 **工作簿内全部已入库 Sheet**（与 §5.1「Excel 多 Sheet」一致）。**服务端必须按当前用户所属部门过滤向量命中**（§5.3.3），用户**看不到**未授权部门范围内的文档片段。**大模型润色**见下节 **§5.2.1**（**G8**，与 §12.4 技术约定一致）。

#### 5.2.1 检索后大模型润色（vLLM + Qwen，**已定**）

- **定位**：在**已完成**向量检索且 **payload 已按部门过滤** 的前提下，对**当前请求命中的 Top-K 文本片段**做 **RAG 式综合与语言润色**；**不替代**检索，也不在未检索到的语料上作答。  
- **推理服务**：**vLLM** 部署，对外提供 **OpenAI 兼容 HTTP API**（`/v1/chat/completions` 等，以实际部署为准）。**默认对接模型**：**通义千问 `Qwen3-30B-Thinking`**；**Thinking** 类模型的额外参数（如 `enable_thinking`、温度、最大 token）在 **TDD** 与现网 vLLM 配置中固定。  
- **连接配置（强制）**：**Base URL、模型名、可选 API Key** 仅通过 **`.env` / 密钥管理**注入，**禁止**写死在源码或提交到仓库。项目组当前联调示例（**可变更**）：http://<YOUR_HOST>:8901/v1/（末尾保留 `/v1/` 与 OpenAI 客户端习惯一致）。  
- **数据流**：服务端将 **用户问题 + 脱敏后的 Top-K 片段**（含 `file_path`、页码/Sheet/行等**引用元数据**）组装为 prompt → 调用 vLLM → 解析回复 → 与原始命中列表一并返回前端。  
- **合规与安全**：**仅服务端**调用 vLLM；提示词须约束 **「不得编造库外事实」**、**引用须对应下方某条检索结果**；**不得**把越权片段送入模型（依赖 §5.3.3 前置过滤）。  
- **产品展示**：检索页在**保留原有片段列表**（§5.1.1）的同时，提供 **「AI 综合/润色」** 区块（可折叠或 Tab）：展示模型输出，并支持 **编号引用**跳转回具体命中行（路径 + 定位信息与 G6 一致）。  
- **降级**：vLLM **超时、5xx 或不可达**时：返回**仅向量检索结果** + 明确提示「智能润色暂不可用」；**不重试拖死**用户主路径（重试策略见 §13.2）。  
- **可观测**：记录 LLM 调用耗时、失败率；是否写入 `audit_logs`（如 `search.rag_synthesize`）由 TDD 与性能评审决定。

#### 5.2.2 Qdrant 自带 Dashboard 与 Web 入口（管理员）

- **是否可在 Web 里使用**：**可以**。Qdrant 提供独立 **Dashboard 页面**，管理员用浏览器打开即可；**不要求**在自研 SPA 内用 iframe 完整「嵌进去」才算可用。  
- **产品要求（强制）**：在 **管理端**（如 **系统管理**、**管理看板**工具条或顶栏「运维」菜单）提供 **`打开 Qdrant 控制台`** 类按钮或链接：**仅知识库管理员**（或更窄的 **运维角色**，TDD）可见；点击后在 **新浏览器标签页**打开 Dashboard（`target="_blank"` / `window.open`，带 `rel="noopener noreferrer"`）。  
- **URL 来源**：由配置项 **`QDRANT_DASHBOARD_PUBLIC_URL`**（或等价名）提供完整地址，写入 **`.env`**，经 **后端只读接口**下发给前端（避免前端写死内网 IP）。示例（开发机）：`http://localhost:6333/dashboard`；生产可改为 **Nginx 反代**后的 `https://kb.example.com/qdrant-dashboard/`（路径以运维为准）。  
- **为何默认新标签页**：Qdrant 响应头常带 **`X-Frame-Options`** / **CSP**，在自研站点内 **iframe 嵌套**易被浏览器拦截；若强需求「页内嵌」，须在 **反向代理**上同域反代并酌情调整安全头（**TDD**，非 M2 默认范围）。  
- **安全警示**：Dashboard 可**绕过**业务层的部门权限直接查看 Collection 与向量数据，须配合 **Qdrant API Key**、**仅内网/管理网段可达**、**禁止公网暴露 6333**；普通用户**不得**看到该按钮，且网络策略上亦应限制访问面。

### 5.3 权限、五级部门与 EHR

#### 5.3.1 组织模型（与 EHR 对齐）

- 公司组织架构在 EHR 中为 **树形结构，最多 5 级**（示例：**品质中心** → **QA 部门** → **下级科室** → …，共 5 层封顶；实际级数以 EHR 为准，产品侧 UI 与接口须支持 **1～5 级**展示与选择）。  
- 知识库维护本地 **`departments` 表**（或通过定期同步与 EHR 一致的镜像表），字段至少包含：**EHR 部门主键**、**父部门 ID**、**层级 depth（1～5）**、**部门名称**、**全路径展示名**（如 `品质中心 / QA部门 / …`）、**同步时间**。  
- **同步策略**：每日**固定时段**与 EHR 对齐数据（**默认每天 `02:00`**，时区与具体 Cron 表达式**可配置**，与 §5.5「凌晨 1:00 文档批处理」**错开**）；**系统管理**支持**手动触发**同步（全量/增量以 TDD 为准）。登录后是否**额外**拉取组织缓存为**可选**（默认依赖定时快照即可）。EHR 不可用时**降级**为使用上次同步快照，并提示「组织数据可能不是最新」；部门合并/撤销时须有**对账任务**（历史文档的 `visible_department_ids` 是否映射需运维规则，可在 TDD 细化）。

#### 5.3.2 上传时：指定「哪些部门可查」

- **上传人**在**上传入口**通过 **树形多选 / 五级联动** 选择允许检索本文档的部门范围。  
- **「含下级」规则（产品默认建议）**：对每一个被选中的部门节点，可勾选 **包含该节点全部下级子部门**（递归至第 5 级）。索引写入前，服务端将选中节点展开为 **部门 ID 集合** `expanded_dept_ids`，去重后：  
  - 写入关系库 **`documents.dept_scope_json`**（或扩展 `acl_json`）保留**原始勾选**（便于 UI 回显与审计）；  
  - 向 Qdrant **每条 point 的 payload** 写入 **`visible_department_ids`** = `expanded_dept_ids`（扁平数组），保证检索过滤无需再递归树。  
- **最小范围**：若业务要求「仅本节点不含下级」，则 `expanded_dept_ids` 仅含该节点 ID。  
- **管理员/特权角色**：可配置「全公司可见」文档（`visible_department_ids` 特殊值如 `["*"]` 或独立 flag），须在 PRD 实现清单与审计中单独列出；默认上传**不允许**跳过部门范围选择（除非角色为系统管理员）。

#### 5.3.3 检索时：用户固定查询范围

- 用户登录后，其 **主属部门**（及可选 **兼职部门** 列表，若 EHR 提供）同步至 **JWT 或会话**，对应 **部门 ID 列表** `user_dept_ids`。  
- **向量检索**（及任何混合检索）在 Qdrant 侧必须附加 **Filter**：`visible_department_ids` **包含** `user_dept_ids` 中**至少一个**（或与企业约定的「主部门优先」策略一致）。  
- **程序化 API（G9）**：**OpenClaw** 等通过 **HTTP API** 发起的检索，与 **浏览器内检索**须走**同一套**服务端逻辑：从 JWT 或 API Key **解析出 `user_dept_ids`（或等价主体）**，再应用本款 Filter；**禁止**提供「绕过部门过滤」的公开检索接口。  
- **效果**：用户**只能**在本人所属部门（ies）被授权的文档集合内看到命中结果，实现 **「固定范围内查询知识」**；跨部门文档即使语义相关也**不得**返回（超级管理员审计模式可单独接口，需二次鉴权与日志）。  
- **与 G4 的关系**：检索 **UI 入口**仍可对全员开放，但**数据面**必须按部门范围过滤，**不再**使用模糊的「全员可查结果集」表述。

#### 5.3.4 写操作与其它

- **写操作**（上传、删、改、手动重索引）：除部门范围外，仍校验 **角色**、**文档所有者** 或 **目录级策略**（与 `cursor-rules` RBAC 一致）。  
- **审计**：记录上传时勾选的部门范围摘要、修改可见范围的操作人及时间；与 **§7.4**、**操作日志页**打通。**检索**行为是否全量写入 `audit_logs` 可按性能与合规**采样或全量**（TDD），看板「按日操作次数」须与最终策略一致。  
- **原「全员可查」口径**：以 **§5.3.3** 为准——检索结果**必须**按部门范围过滤；若需真正的全公司公开库，通过 **显式「全公司可见」** 文档类型与审计实现，而非默认无过滤。

### 5.4 并发与性能（目标量级）

- 约 **20 人同时**使用：检索与上传均通过 **API 无状态扩展** + **队列削峰**；不向同步 HTTP 塞满解析与 embedding。  
- 监控：Qdrant 延迟、队列深度、任务失败率、Worker CPU/GPU。

### 5.5 定时与队列

- **即时队列**：上传默认进入 **高优先级**；Worker 限制并发，避免占满 CPU/GPU。  
- **凌晨 1:00 批处理**（可配置 TZ）：在同一调度窗口内**至少**包含：  
  1. **新增/变更检测**、**失败重试**、**全量补偿**（`night_batch_flag`、hash/mtime 不一致、`pending_index` 等）；  
  2. **已删除文档的向量清理（强制）**：对 **Web 端已标记删除**、或 **元数据行已删但向量清理未确认成功** 的 `doc_id`，在 **Qdrant** 中执行 **按 `doc_id` 过滤删除**（`delete_vectors` 任务或批内等价逻辑），直至校验**无残留 points**（可对单 `doc_id` count 或抽样检索验证，TDD 固定）；  
  3. **孤儿向量对账（建议强制）**：枚举或采样 **Qdrant** 中存在的 `doc_id`，与 **`documents` 表**（或归档表）对照，对**库中已不存在**的 `doc_id` **删除全部向量**，避免「文件已删、仍能搜到旧片段」。  
  使用 **低优先级** 队列或与即时队列共享 Worker 但 **限流/配额**；**②③** 与 **①** 可同一 Job 分阶段执行，失败须**可重试**并记日志/看板指标。  
- **凌晨 2:00（可配置）EHR 同步**：由 **scheduler / ehr-sync** 触发，拉取或消费 **部门树 + 人员与主属部门** 等，写入 **SQL Server**（§7.2.1、§7.2.2）；与上文文档批处理**独立调度**，避免同一时刻压垮外网/中间库。  

### 5.6 检索质量（建议纳入迭代）

- **混合检索**：向量语义 + **BM25/关键词**（或稀疏向量）融合，兼顾专有名词与概念问法（业界 RAG 栈常见做法）。  
- **重排序（Rerank）**：对 Qdrant Top-K 候选用 **Cross-Encoder** 等模型二次排序，提升答案引用片段相关性（权衡延迟与 GPU）。  
- **语义分块**：标题/章节感知的分块策略，减少chunk跨主题导致的噪声（可与 LlamaIndex / LangChain 等框架对齐）。

### 5.7 登录与品牌视觉（强制）

- **独立登录页**：系统必须提供**全应用统一入口**的登录界面；未持有有效凭证（如 JWT）的用户**仅可访问登录及相关公开路由**（若后续增加「找回密码」等），**禁止**进入检索、文档库、任务中心等主功能（与 `cursor-rules.md` 路由守卫一致）。  
- **登录流程（产品）**：**用户名（登录 ID）= EHR 人员唯一标识**（工号/员工 ID 等，**字段名与 EHR 接口对齐**，在 TDD 固定）；**密码**为知识库本地口令。可选「记住我」「验证码」；登录成功后进入**首页/检索**（具体默认落地页可在 M2 评审拍板）；**退出登录**清除本地 Token 与用户信息并回到登录页。  
- **账号与密码策略（与 EHR 配合）**：EHR 同步**首次在本库创建**的用户，默认登录密码为 **`123`**（仅服务端存 **bcrypt 等哈希**，禁止明文落库，与 §5.8 一致）。**普通用户**与**知识库管理员**均须能**修改本人密码**（旧密码校验）；管理员另可按 RBAC **重置他人密码**（如生成临时口令或恢复默认 `123` 并**强制首次登录改密**，具体二选一在 TDD 定案），操作写入 **§7.4 审计**。  
- **视觉基调：暗红色**：整站以 **暗红色系** 作为主品牌色（用于主按钮、关键链接、顶栏/侧栏强调、焦点环等）；背景建议 **深灰/近黑** 或深色侧栏 + 浅灰内容区（二选一由 UI 稿定），须满足 **正文与按钮文字的对比度**（目标不低于 **WCAG AA**）。  
  - *设计交付参考色（可替换）*：主色可与下方 Logo 取色对齐，例如 **`#A32323` / `#911D1D`**（深红）、深色衬底 `#1A1A1A`、中性内容区 `#F5F5F5`～`#FFFFFF`；次级强调可比主色略亮或略暗一档，最终以设计稿为准。  
- **Logo**：登录页及管理端顶栏等位置须展示 **`logo.png`**。**唯一源文件路径**：`assets/branding/logo.png`（当前已入库：**彩迅集團 / Express LUCK Group** 横版标识；图标为暗红图形 + **黑色中英文**，带灰色立体阴影）。前端构建时复制或引用至 `public/logo.png` 或 `src/assets/logo.png`，登录页使用 `<img alt="彩迅集团知识库">`（或企业指定文案）。换标时只更新 `assets/branding/logo.png`；若根目录存在重复的 `logo.png`，应避免双源维护，以 `assets/branding/` 为准。  
- **组件库主题**：若采用 Element Plus，须通过 **主题变量 / CSS 覆盖** 将 `primary` 映射为与 Logo 红 **同色相、可微调明度** 的色值，避免默认蓝与品牌冲突。

#### 5.7.1 Logo 与暗红界面：层次与防突兀（强制参考）

当前 Logo **本身已是暗红色**，若整页再用大面积同色背景，易出现「糊成一团」或图标与底融在一起。实施时须遵守 **明度分层**，而非再堆叠同色块：

| 策略 | 说明 |
|------|------|
| **浅色容器承托原稿** | 登录页 Logo 建议放在 **白 / 近白 / 浅灰卡片**（如 `#FFFFFF`、`#F7F4F4`）内，卡片外再用 **深灰/深红偏黑** 大背景，形成 **对比**，原稿彩色 Logo 清晰可辨。 |
| **避免红底叠红标** | **禁止**在 **与 Logo 主红接近的纯色暗红底** 上直接放置未经处理的彩色 Logo（图标红色会贴边）。若必须在深色顶栏展示彩色稿，应为 Logo 区保留 **左侧浅色条** 或 **足够内边距的浅底块**。 |
| **深色顶栏专用变体（推荐备品）** | 若产品需要在 **连续深色/暗红导航条** 上展示标识，应增加 **`logo-mono-light.png`（反白/浅色单色稿）** 或由设计输出 **反白 SVG**；不得强行把黑字彩色稿压在深红条上导致文字不可读。 |
| **主色用量** | UI **primary** 用于按钮、选中 Tab、关键链接等 **点状/带状强调**；**大面积背景** 以中性灰、浅表面色为主，暗红只做 **点缀与导航语义**，避免与 Logo 抢同一视觉层。 |
| **可加细微分离** | 在浅底上一般无需描边；若深色场景中必须用彩色稿，可对图标外沿加 **极细浅色描边或极弱外发光**（设计评审后），增强与背景的分离度。 |

### 5.8 接口与工程规范（与 `cursor-rules.md` 对齐）

以下摘录自仓库根目录 **`cursor-rules.md`**，实现本知识库前后端时**默认遵守**（若与本文其他章节冲突，以**安全与合规**优先；数据库选型见 §12.0）。

| 类别 | 约定 |
|------|------|
| **编码与缩进** | UTF-8；缩进 **4 空格**，禁止 Tab。 |
| **命名** | 变量/函数小驼峰；常量全大写下划线； Vue 组件大驼峰；**文件/目录短横线**；数据库表/字段下划线（表名单数如 `document`、`index_job` 可与 PRD §7 对齐）。 |
| **接口返回** | 统一 JSON：`{ "code": 200, "msg": "提示", "data": {} }`；**200** 成功；**401** 未登录或 Token 无效/过期；**403** 无权限；**404** 资源不存在；**500** 服务器错误（`msg` 友好、**不暴露**堆栈与敏感信息）。 |
| **列表与分页** | 列表类接口**必须分页**；参数统一 **`page`、`pageSize`**；`pageSize` **上限建议 100**，禁止一次返回全表。**操作日志**、**看板明细下钻列表**（若有）遵守同一约定。 |
| **认证** | 登录成功后颁发 **JWT**；前端与 **G9 API** 均可使用 **`Authorization: Bearer <token>`**；另支持 **API Key**（如 **`X-API-Key`** 或约定 Bearer 前缀，TDD/OpenAPI 固定），绑定服务账号或真实用户并**继承其部门范围**；后端保护路由须校验；**敏感配置仅 `.env`**，禁止代码内明文账号密码与密钥。 |
| **安全红线** | 禁止 `v-html` 渲染不可信用户输入；密码**禁止明文存储**（bcrypt 等）；SQL **参数化**防注入；上传校验类型与大小；登录 **防暴力破解**（如连续失败锁定 + IP 限流，见 cursor-rules 细则）。 |
| **交互** | 后端接口 `try/catch` 统一错误形态；前端请求 **Loading** 与 **错误提示**（如 Element Plus `ElMessage`）。 |
| **日志** | 登录日志、操作日志、错误日志（与 §7 `audit_logs`、运维要求一致）。 |

### 5.9 对外 HTTP API（OpenClaw / 系统集成，**G9**）

除 **Web SPA** 外，须暴露 **RESTful HTTP API**（与前端 **同源** `/api` 或由 **Nginx** 统一反代），使 **OpenClaw**、自动化流水线、其它内网服务**无需浏览器**即可调用知识库能力。

| 主题 | 要求 |
|------|------|
| **OpenAPI 3** | 仓库维护 **`openapi.yaml`（或 JSON）**，描述路径、请求/响应模型、鉴权方式；可由此生成各语言 Client 或导入 OpenClaw / API 调试工具。 |
| **检索（必选）** | 提供 **知识向量检索** 接口（如 `POST /api/v1/search`，具体路径在 OpenAPI 冻结）；请求体至少含 **查询文本**、**topK**（上限封顶）、可选 **`includeRag`**（是否走 **G8** 润色，默认与 Web 策略一致）；响应 **`data`** 与 **§5.1.1** 对齐（得分、片段、`file_path`、页码/幻灯片/Sheet/行等），可选返回 **`ragAnswer` + `citations`**。 |
| **扩展（可选，TDD）** | 文档上传、任务状态查询、文档列表等可按里程碑逐步开放；须**同样**走 RBAC 与部门策略。 |
| **鉴权** | ① **JWT**：与 Web 登录一致，从 Token 解析用户及 **`user_dept_ids`**。② **API Key**：供 OpenClaw 长期集成；**绑定**到具体用户或服务主体，**继承该主体的部门可见范围**；支持**创建、吊销、轮换**；密钥**仅存哈希**，创建时**一次性**展示明文（与常见 SaaS Key 实践一致）；调用写入 **`audit_logs`**（`actor_login_id` / 服务名 + `search.query` 等）。 |
| **限流与安全** | 对 **API Key** 与 **IP** 做限流（见 §13.2）；**HTTPS**（生产）；禁止在 URL Query 传 Key。 |
| **错误与分页** | 遵守 **§5.8** `code` / `msg` / `data`；列表类接口遵守 **`page` / `pageSize`**。 |

**与 OpenClaw 的集成说明（产品）**：OpenClaw 侧配置 **Base URL**、**API Key**（或 OAuth/JWT 获取流程，TDD）即可调用检索接口；返回结构稳定后，可在 OpenClaw 内做**引用展示**或二次对话（仍受本库权限约束）。

以下为推荐 **Docker Compose 服务划分**（名称可调整）。

```
                    │   Nginx     │ 可选：TLS、限流、反代
                    └──────┬──────┘
                           │
              ┌────────────┴────────────┐
              │          API            │  FastAPI / 等价
              │ 鉴权·上传·检索·**对外 API（G9）**·任务创建  │
              └────────────┬────────────┘
                           │
     ┌─────────────────────┼─────────────────────┐
     │                     │                     │
     ▼                     ▼                     ▼
┌─────────┐          ┌──────────┐         ┌───────────┐
│SQL Server│         │  Redis   │         │  Qdrant   │
│ 元数据   │          │ 队列/缓存 │         │  向量库    │
│ 与任务   │          │  可选     │         │  :6333    │
└─────────┘          └────┬─────┘         └───────────┘
                           │
                    ┌──────┴──────┐
                    │   Worker    │ 可水平扩展多个副本
                    │ 解析·嵌入   │
                    │ ·upsert    │
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │ 文件存储     │
                    │ Volume/S3   │
                    └─────────────┘

┌─────────────┐
│   Frontend  │  SPA；上传页含「可检索部门」五级树（§5.3.2）
└─────────────┘

┌─────────────┐
│  公司 EHR   │  组织/部门树、人员主属部门（REST / 中间库 / 消息）
└──────▲──────┘
       │ 默认每日 **02:00**（可配置）同步 → **API** 写入 `departments` / `users`；可手动触发
```

| 服务 | 职责 |
|------|------|
| **api** | REST/WebSocket：**OpenAPI 文档（G9）**、登录、**JWT + API Key 鉴权**、文档 CRUD、创建索引任务、**程序化检索**（含 **G8** 可选润色）、管理接口；**EHR 同步入口**（Webhook/定时拉取由 **scheduler** 或独立 job 调用）。 |
| **worker** | 消费队列：解析 → 分块 → embedding → Qdrant upsert/**按 doc_id delete**；处理 **`delete_vectors` / 夜间对账删除**；写回任务状态。 |
| **sqlserver** | 用户、文档元数据、权限、**任务表**、审计日志（可选分表）；连接参数见 **§12.0**。 |
| **redis** | 消息队列、分布式锁、限流计数（可选；初期也可用 DB 轮询代替队列）。 |
| **qdrant** | 向量存储（现有 compose）。 |
| **file-storage** | 宿主机 bind mount 或 MinIO 等；API/Worker 挂载同一逻辑路径或预签名 URL。 |
| **nginx** | 可选：TLS、静态前端、`/api` 反代。 |
| **ehr-sync**（可选） | 独立定时任务：**默认每天 `02:00`**（可配置 TZ/Cron）拉取/消费 EHR 变更，写 **SQL Server** `departments` 与用户部门等字段；失败重试与对账见 **§12.3**。 |

**批次调度**：单独 **scheduler** 容器运行 `cron` 或调用 API：其一触发 **凌晨 1:00 文档批处理**（与 worker 批处理入口一致）；其二触发 **EHR 同步**（默认 **02:00**，亦可托管为 K8s CronJob）。两类任务**不得混为同一无差别 Job**，以免失败域耦合。

## 7. 数据模型与任务表

### 7.1 核心实体关系（概念）

- **User** — 账户与组/角色；**主属部门 ID**、**兼职部门 ID 列表**（与 EHR 同步，用于 §5.3.3 检索过滤）。  
- **Department**：EHR 镜像组织节点，**树深最多 5 级**（§5.3.1）。  
- **Document**：一条逻辑文档（`doc_id`），关联存储路径、hash、**部门可见范围**（`dept_scope_json`）、当前版本。  
- **IndexJob**：一次索引执行任务（即时或批处理），与 `doc_id`、优先级、状态绑定。  
- **AuditLog**（可选）：写操作与敏感读操作。

> **SQL Server 类型映射**（§12.0）：下列逻辑类型在 T-SQL 中可对应为：`JSONB` → **NVARCHAR(MAX)**（JSON 文本，可选 `ISJSON`）；`TIMESTAMPTZ` → **DATETIMEOFFSET**；`UUID` → **UNIQUEIDENTIFIER**；`ENUM` → **VARCHAR** + **CHECK** 或码表；`BOOLEAN` → **BIT**。

### 7.2 表：`documents`（文档元数据）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | UUID | 主键，对应对外 `doc_id`。 |
| `title` | VARCHAR | 显示名。 |
| `storage_key` | VARCHAR | 对象存储 key 或相对路径。 |
| `mime_type` | VARCHAR | 如 `application/pdf`。 |
| `size_bytes` | BIGINT | 文件大小。 |
| `content_hash` | VARCHAR(64) | SHA-256，用于变更检测与幂等。 |
| `indexed_content_hash` | VARCHAR(64) \| NULL | 上次成功写入 Qdrant 时对应的 hash。 |
| `status` | ENUM | `draft` / `pending_index` / `indexed` / `failed` / `disabled` / **`deleted`**（用户已在 Web 删除，**待/正**清理向量与存储；清理完成后可**物理删行**或归档，TDD）。 |
| `owner_user_id` | UUID | 上传者。 |
| `dept_scope_json` | JSONB | **部门检索范围**（§5.3.2）：保存上传时勾选的原貌，如 `{ "nodes": [{"dept_id":"…","include_children":true}], "is_company_wide": false }`。 |
| `acl_json` | JSONB | 可选：补充角色/用户组等**非部门** ACL；与 `dept_scope_json` 同时生效时取**交集**（以 TDD 为准）。 |
| `created_at` / `updated_at` | TIMESTAMPTZ | |
| `last_opened_at` | TIMESTAMPTZ \| NULL | 可选。 |
| `night_batch_flag` | BOOLEAN | 是否参与凌晨批处理扫描（默认 true）；**`deleted`** 文档**仍须**参与 **§5.5** 的向量清理扫描（或单独对账队列），直至 Qdrant 无该 `doc_id`。 |
| `deleted_at` | TIMESTAMPTZ \| NULL | 可选：Web 端发起删除的时间，便于审计与 1:00 对账排序。 |

**索引**：`(status)`, `(content_hash)`, `(updated_at)`；建议 **`(status, deleted_at)`** 供待清理删除任务扫描。

### 7.2.1 表：`departments`（EHR 组织镜像）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | UUID | 本库主键（可与 EHR id 一致或映射）。 |
| `ehr_dept_id` | VARCHAR | EHR 系统部门唯一标识（对接主键）。 |
| `parent_ehr_dept_id` | VARCHAR \| NULL | 父部门 EHR ID；根节点为空。 |
| `depth` | TINYINT | **1～5**，层级深度。 |
| `name` | NVARCHAR | 部门名称。 |
| `path_display` | NVARCHAR | 全路径展示，如 `品质中心 / IQC` / `品质中心 / QA / …`。 |
| `sort_order` | INT \| NULL | 同级排序（可选）。 |
| `synced_at` | DATETIMEOFFSET | 最近成功同步时间。 |
| `is_deleted` | BIT | EHR 侧已撤销时软删标记，供对账。 |

**索引**：`(ehr_dept_id)` 唯一；`(parent_ehr_dept_id)`；`(depth)`。

### 7.2.2 用户与部门（`users` 表扩展建议）

| 字段 | 类型 | 说明 |
|------|------|------|
| `login_id` / `ehr_user_id` | NVARCHAR | **登录用户名**，与 **EHR 人员唯一 ID** 一致（与 §5.7 对齐）；唯一索引。 |
| `password_hash` | NVARCHAR | 本地登录口令哈希；**禁止明文**。EHR 同步新建用户时写入 **默认密码 `123`** 的哈希。 |
| `password_changed_at` | DATETIMEOFFSET \| NULL | 可选：用于策略与审计。 |
| `must_change_password` | BIT | 可选：管理员重置或安全策略要求下次登录改密。 |
| `primary_dept_id` | UUID \| NULL | FK → `departments.id`，**主属部门**。 |
| `dept_ids_json` | NVARCHAR(MAX) \| NULL | 兼职/多部门 JSON 数组（若 EHR 支持），检索时合并进 `user_dept_ids`。 |

**每日定时同步（默认 02:00）**从 **EHR** 拉取并更新部门与人员归属；**不在 EHR 回写**知识库密码。若 EHR 标记人员离职/禁用，本库应同步 **禁止登录**（TDD 细化状态字段）。

### 7.3 表：`index_jobs`（任务表 — 核心）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | UUID | 主键。 |
| `document_id` | UUID | FK → `documents.id`。 |
| `job_type` | ENUM | `immediate_upload` / `manual_reindex` / `scheduled_batch` / `delete_vectors` / **`nightly_reconcile_delete`**（可选：由 1:00 调度批量入队的对账删除，与 `delete_vectors` 二选一或并存，TDD）。 |
| `priority` | SMALLINT | 数值越大越优先；即时上传 > 批处理。 |
| `status` | ENUM | `queued` / `running` / `success` / `failed` / `cancelled`。 |
| `attempt_count` | INT | 重试次数。 |
| `max_attempts` | INT | 默认 3～5。 |
| `error_code` | VARCHAR \| NULL | 机器可读错误码。 |
| `error_message` | TEXT \| NULL | 可读错误信息。 |
| `payload_json` | JSONB | 扩展：如 `dry_run`、`embedding_model_version`。 |
| `started_at` / `finished_at` | TIMESTAMPTZ \| NULL | |
| `created_at` | TIMESTAMPTZ | 入队时间。 |
| `created_by` | UUID \| NULL | 触发人；系统任务为空。 |
| `worker_id` | VARCHAR \| NULL | 认领 Worker 标识。 |

**约束与索引**：

- 部分业务可约定：同一 `document_id` 在 `queued|running` 时仅允许一条即时类任务（应用层或唯一部分索引）。  
- 索引：`(status, priority DESC, created_at)` 供出队；（`document_id`）；（`status, job_type`）。

### 7.4 表：`audit_logs`（**强制**，支撑 G7）

业务上须**持久化**用户关键行为，供 **操作日志页**逐条查询与 **看板**按日聚合。实现可用 SQL Server 表 + 索引；`metadata_json` 可用 **NVARCHAR(MAX)** 存 JSON。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGINT IDENTITY | 主键。 |
| `actor_user_id` | UUID \| NULL | 操作人；系统任务可为空并配合 `action` 区分。 |
| `actor_login_id` | NVARCHAR(128) \| NULL | 冗余 **EHR 登录 ID**（便于日志页展示与按账号筛选，与 §7.2.2 对齐）。 |
| `action` | NVARCHAR(64) | 机器可读类型，建议统一前缀：`auth.login` / `auth.logout` / `auth.password_change` / `search.query` / `search.rag_synthesize`（**G8** 润色调用，可选全量/采样） / `doc.upload` / `doc.delete` / `doc.update` / `job.retry` / `admin.user_password_reset` / `admin.ehr_sync_trigger` 等（**完整枚举在 TDD 冻结**）。 |
| `target_type` | NVARCHAR(32) \| NULL | 如 `document` / `job` / `user` / `system`。 |
| `target_id` | UNIQUEIDENTIFIER \| NULL | 被操作对象 ID，无则空。 |
| `summary` | NVARCHAR(512) \| NULL | 人类可读短描述（如文件名截断、检索 query 摘要），**禁止**存全文敏感文档内容。 |
| `metadata_json` | NVARCHAR(MAX) \| NULL | 扩展：IP、User-Agent、请求 id、错误码等。 |
| `created_at` | DATETIMEOFFSET | 事件发生时间（UTC 或统一时区，与看板「按日」统计一致）。 |

**索引（建议）**：`(created_at DESC)`；`(actor_user_id, created_at DESC)`；`(action, created_at DESC)`。  
**按日操作统计**：看板「按天用户操作次数」可由 SQL **按 `CAST(created_at AS DATE)` + `actor_user_id`（或全体）** 聚合；数据量大时可增加**日汇总表**或定时任务物化（TDD 选型）。

**写入责任**：登录/登出、检索（可采样或全量，见 TDD）、**API Key 发起的检索**、文档上传/删改、任务重试、管理员重置密码、手动触发 EHR 同步等**须打点**；具体是否记录每次检索的 query 全文以**合规与性能**评审为准，至少记录「发生了一次检索」与可选摘要。

| 字段 | 类型 | 说明 |

| `name` | NVARCHAR | OpenClaw / 集成名称，便于管理。 |
| `created_at` / `revoked_at` | DATETIMEOFFSET | 吊销后拒绝校验。 |
| `last_used_at` | DATETIMEOFFSET \| NULL | 可选。 |

**索引**：`(key_hash)`；（`bound_user_id`）。

## 8. 状态机（任务）

```text
queued → running → success
              ↘ failed （attempt_count < max_attempts → 可重回 queued）
              ↘ cancelled
```

- **删除文档（Web 即时路径）**：用户确认删除后，插入 **`job_type=delete_vectors`**（高或中优先级）；Worker **先**按 `doc_id` **删尽 Qdrant points** 并校验，**再**删存储对象与 **`documents` 行**（或先置 `status=deleted` 再异步清存储，TDD 二选一须**保证**向量先清）。  
- **删除文档（凌晨 1:00 补偿路径，G3）**：对 **`status=deleted`** 或 **`delete_vectors` 失败/超时** 仍残留的文档，批处理**再次**入队删除或**内联**执行 Qdrant 清理；对 **Qdrant 孤儿 `doc_id`** 执行删除（§5.5）。**验收**：被用户删除的文件，**次日 1:00 任务成功后**检索**不得**再命中该文档内容。  
- **批处理**：对 `indexed_content_hash IS DISTINCT FROM content_hash` 或 `status=pending_index` 的文档创建 `scheduled_batch` 任务；**与**对账删除**同一 Cron 内顺序执行**或**分队列并行**（TDD），不得互相阻塞导致删除永远不被执行。

### 12.2 与 Qdrant 客户端的衔接

- 应用侧统一使用 **`qdrant-client`**（HTTP/gRPC）；生产环境可对 gRPC 开启连接池或择优路由。

- **Dashboard**：容器默认映射 **`:6333`**（HTTP REST + Web UI）；**业务应用**连接 Qdrant 用内网地址（如 `http://qdrant:6333`），与 **`QDRANT_DASHBOARD_PUBLIC_URL`**（给**管理员浏览器**用的可解析 URL，见 **§5.2.2**）可不同——后者常为主机名、反代域名或 `localhost`。

### 12.3 身份与集成

- **主方案（本阶段）**：**本地账号 + JWT**：登录名为 **EHR 人员 ID**（与 §5.7、§7.2.2 一致）；API 使用 **JWT + RBAC** 与文档 ACL、部门范围（§5.3.3）联合判定。若后续接入 **OIDC / LDAP / 企业微信** 等 SSO，与本地账号**并存或迁移**策略在 TDD 单独评审。  
- **EHR 对接（组织与人员）**：通过企业提供的 **REST/中间库/消息** 同步 **5 级部门树**、**人员主属部门**及用于登录的 **人员唯一 ID**（字段见 §7.2.1、§7.2.2）；连接串与凭据仅存 **`.env`**。同步 **默认每日 `02:00`**（**可配置**），须实现**失败重试、增量同步、对账日志**；**不在 EHR 存储**知识库密码。  
- **Provisioning 与密码**：同步发现**新用户**时在本库创建行并设置 **默认密码 `123`**（仅存哈希）；**用户与管理员**均可**修改本人密码**；管理员可**重置他人密码**（§5.7）。  
- **密钥**：Embedding 与 **vLLM**（§12.4）若需 **API Key**，**仅服务端**持有，经密钥管理（环境注入或 Vault）下发。

| 项 | 约定 |

## 13. 运行稳定性、高可用与运维（SRE）

> 本章要点综合 Qdrant 官方《Vector Search in Production》等资料中的生产教训：内存与磁盘、索引与过滤、备份与扩缩容。

### 13.1 Qdrant 侧（向量库）

| 主题 | 建议 |
|------|------|
| **内存与磁盘** | 控制热集尽量驻留 RAM；不足时评估 **`on_disk` / memmap** 与 **量化（Scalar/Binary）** 以降低内存与 I/O 抖动。 |
| **Payload 索引** | 对**所有参与过滤/排序**的 payload 字段建立 **payload index**，避免大量向量先召回再过滤导致 CPU 与延迟飙升；**必须**为 **`visible_department_ids`**（数组/keyword 等按 Qdrant 类型选型）建索引，以支撑 §5.3.3 部门过滤。 |
| **HNSW 参数** | 平衡 `ef` 等与延迟/召回；变更后需在业务数据集上**回归评测**。 |
| **存储介质** | 生产环境使用 **本地 SSD/NVMe**；避免将 Qdrant 数据目录放在 **NFS** 等不符合 POSIX 或延迟不稳的共享盘上（参见官方安装/运维文档）。 |
| **备份与恢复** | 制定 **快照（Snapshot）** 策略与恢复演练周期；WAL/存储路径规划写入运维 Runbook。 |
| **安全** | API Key、网络隔离；若多团队共用集群可评估 **JWT/RBAC**（按官方安全文档实施）。**Dashboard** 与 REST 同端口时，须**限制访问源 IP/VPN**，且**勿对公网开放**；与 **§5.2.2** 一致。 |
| **监控** | 对接 **Prometheus** 指标；关注查询延迟、索引构建、磁盘与内存饱和度。 |
| **扩展** | 单机不足时按官方文档考虑 **分布式/多副本**（多节点、共识与 PVC 等），与第 6 章架构升级路线一致。 |

**参考链接**：[Vector Search in Production — Qdrant](https://qdrant.tech/articles/vector-search-production/)，[Storage / Indexing / Optimization — Qdrant 文档](https://qdrant.tech/documentation/manage-data/storage/)

### 13.2 应用与任务管线

| 主题 | 建议 |
|------|------|
| **健康检查** | API：`/health`（存活）、`/ready`（依赖 DB/Redis/Qdrant 就绪）；Worker：心跳写入 Redis 或 DB。 |
| **看板数据来源** | **文档数**等来自 **SQL Server** 聚合；**向量点数**来自 **Qdrant** `collection` 统计接口（或定时缓存校准，避免高频打满向量库）；**按日操作量**来自 **`audit_logs`** 聚合或日汇总表（§7.4）。 |
| **超时与重试** | 对外部 embedding 使用**指数退避 + 最大重试**；队列任务 `max_attempts` 与**死信表**人工处理。 |
| **幂等与并发** | 同一 `document_id` **互斥**索引（分布式锁或唯一约束）；删除与重索引顺序：**先删向量再删元数据**或补偿任务。 |
| **背压** | API 对上传 QPS、单用户并发 job **限流**；**G9 API Key / 公网暴露面**须**单独配额**（防 OpenClaw 或脚本误刷）；队列长度超阈**告警**并暂停低优先级入队。 |
| **熔断与降级** | Qdrant 或 embedding 异常时：检索返回 **503 + 重试建议**；可选 **仅关键词/BM25** 降级（若已实现混合检索）。**vLLM** 异常或超时时：**仍返回向量检索结果**，LLM 部分失败提示，见 **§5.2.1**。 |
| **版本与迁移** | Embedding 模型升级时：`embedding_model_version` 写入任务 payload；支持**按批次重嵌入**与兼容期双集合（灰度）。 |

### 13.3 SLO 与演练（建议目标，可按企业调整）

| 指标 | 目标（示例） |
|------|----------------|
| 检索 API P95 延迟 | **不含 LLM**：目标约 2s 内（P95；含 embedding + Qdrant）。**含 G8 润色**：单独统计，目标由部署侧与 **Qwen3-30B-Thinking** 延迟共同决定（建议 TDD 给出 P95 上限，如 30～120s 量级可调）。 |
| 索引任务从 `queued` 到 `success`（小文件量级） | 目标数分钟内（视 Worker 与模型而定） |
| 月度可用性 | 建议不低于 99.5%（内网单机房可按实际下调并写明维护窗） |

- **混沌/演练**：每季度 **Qdrant 快照恢复**、**SQL Server 备份还原 / 时间点恢复**、**单 Worker 宕机** 验证任务不丢不重。  
- **Runbook**：常见事故（磁盘满、队列堆积、Redis 不可用）的标准处理步骤与联系人。

### 13.4 安全与合规（稳定性相关）

- **审计日志** tamper-aware 存储或定期归档。  
- **PII**：若文档含个人信息，检索结果展示前 **脱敏策略** 与权限一致。  
- **依赖扫描**：CI 对镜像与 Python 依赖做漏洞扫描（与「运行稳定」相关的供应链风险）。
